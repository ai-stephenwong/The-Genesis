# Bug Report — Omnichat v1 — Deployment Round 1 — 2026-03-21

## Source
First staging deployment attempt on 2026-03-20 / 2026-03-21.
All findings surfaced during `wrangler deploy --env staging` and `npx vercel --prod` execution.
This is a **second bug batch**, distinct from Pipeline Run 1 (code defects).
These defects are exclusively **deployment-time and build-time failures**.

## Key Observation
All issues below were discovered only when credentials were provided and actual
cloud deployment commands were executed. **None were caught by any pipeline agent
(code-reviewer, security-auditor, compliance-officer) during the code review cycle.**
The compliance officer's required Live Integration Smoke Test was deferred; had it
been performed against an earlier staging deploy, these would have surfaced before
the final deployment run.

## Bug Inventory

### Critical — Platform Runtime (DEPLOY-CRIT)

| ID | Description | File(s) | Agent |
|---|---|---|---|
| DEPLOY-CRIT-01 | Pure-JS argon2id (m=65536, t=3, p=4) exceeded Cloudflare Workers CPU time limit — Workers error 1102 thrown on every login attempt. The architect's Platform Runtime Compatibility Matrix documented native `argon2` as incompatible and recommended pure-JS `argon2id`, but did not benchmark the pure-JS implementation's CPU cost against the Workers CPU budget (10–30ms). Pure-JS argon2id with standard parameters requires ~200–400ms CPU, far exceeding the limit. Fix required: replace with PBKDF2-SHA256 (600,000 iterations) using native Web Crypto API (`crypto.subtle`), which executes in sub-millisecond time in V8. | `src/lib/password.ts`, `package.json` | solution-architect |
| DEPLOY-CRIT-02 | Neon HTTP/WebSocket serverless driver bypasses Cloudflare Hyperdrive — all database queries from the deployed Worker hit Neon's proprietary HTTP endpoint instead of the Hyperdrive TCP proxy, making Hyperdrive's connection pooling and TCP routing completely ineffective. DB health check returned `db: false` on every request. The architecture mandated Hyperdrive for DB connections but approved `@neondatabase/serverless` without verifying that this driver routes through Hyperdrive. Hyperdrive requires a standard TCP PostgreSQL driver; only `pg` (node-postgres) or `postgres.js` with `nodejs_compat` flag are intercepted by the proxy. Fix required: replace `@neondatabase/serverless` with `pg` (node-postgres) + `drizzle-orm/node-postgres`. | `src/db/index.ts`, `package.json`, `wrangler.toml` | solution-architect |

### Major — Deployment Configuration (DEPLOY-MAJ)

| ID | Description | File(s) | Agent |
|---|---|---|---|
| DEPLOY-MAJ-01 | `wrangler.toml` contained `[PLACEHOLDER: ...]` strings for all Hyperdrive IDs, KV namespace IDs, R2 bucket names, and Queue names — wrangler config validation rejected the file on first deploy. Additionally, `usage_model = "standard"` (deprecated in wrangler 4.x) produced validation errors. Additionally, cron expression `0 3 * * 0` (numeric day-of-week) is invalid in Cloudflare Workers — must use `SUN`. Additionally, worker `queue` handler was exported as a named export (`export const queue`) which Cloudflare does not recognise; must use `export default { fetch, scheduled, queue }` pattern. | `wrangler.toml`, `src/index.ts` | devops-engineer |
| DEPLOY-MAJ-02 | Cloudflare Queues must be created before the Worker that references them can be deployed — the `[[queues.consumers]]` and `[[queues.producers]]` bindings in `wrangler.toml` reference queues (`omnichat-media-variants-dev`, `omnichat-media-variants-staging`, `omnichat-media-variants-production` and their DLQs) that did not exist. Wrangler deployment aborted with "queue does not exist" errors for all three environments. Six queues required manual `wrangler queues create` before first deploy. | `wrangler.toml` | devops-engineer |
| DEPLOY-MAJ-03 | `omnichat-v1-web/vercel.json` had `"framework": "nextjs"` for a Vite/React SPA — Vercel detected the setting, attempted a Next.js build, and failed with "No Next.js version detected." Additionally, the rewrite rule referenced `_next/` static paths (Next.js convention) rather than `assets/` (Vite convention), and the static asset cache header targeted `/_next/static/` rather than `/assets/`. The web and CMS frontends are both Vite SPAs; only the CMS vercel.json was correct. | `omnichat-v1-web/vercel.json` | developer |
| DEPLOY-MAJ-04 | Both frontend projects failed `tsc` compilation on Vercel due to multiple TypeScript strict-mode errors: (1) `import.meta.env` type errors across all files — `vite-env.d.ts` was not created, so `ImportMeta.env` was unknown; (2) `vitest/config` not used for test config (used `vite` defineConfig instead, which does not accept a `test` property); (3) missing test setup file (`src/test/setup.ts` absent in web project); (4) `noUnusedLocals`/`noUnusedParameters` violations across multiple source and test files (unused imports, unused destructured variables); (5) missing npm packages: `react-hook-form`, `@hookform/resolvers`, `zod` absent from `omnichat-v1-web/package.json` despite being imported in `ContactForm.tsx`; (6) `@radix-ui/react-badge` listed in CMS dependencies — this package does not exist in the npm registry; (7) `@hey-api/openapi-ts@^0.39.3` does not exist — correct version is `^0.94.0`; (8) `vitest@^1.6.0` incompatible with `@cloudflare/vitest-pool-workers` which requires `vitest@"2.0.x - 2.1.x"`; (9) YAML parse error in `api-spec.yaml` — unquoted colon-space in a description string broke the OpenAPI spec file. | `src/vite-env.d.ts`, `vite.config.ts`, `package.json` (both frontends), `api-spec.yaml` | developer |
